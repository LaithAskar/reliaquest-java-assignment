## Problem Statement

Your employer has recently purchased a license to top-tier SaaS platform, Employees-R-US, to off-load all employee management responsibilities.
Unfortunately, your company's product has an existing employee management solution that is tightly coupled to other services and therefore 
cannot be replaced whole-cloth. Product and Development leads in your department have decided it would be best to interface
the existing employee management solution with the commercial offering from Employees-R-US for the time being until all employees can be
migrated to the new SaaS platform.

Your ask is to expose employee information as a protected, secure REST API for consumption by Employees-R-US web hooks.
The initial REST API will consist of 3 endpoints, listed in the following section. If for any reason the implementation 
of an endpoint is problematic, the team lead will accept **pseudo-code** and a pertinent description (e.g. java-doc) of intent.

Good luck!

## Endpoints to implement (API module)

_See `com.challenge.api.controller.EmployeeController` for details._

getAllEmployees()

    output - list of employees
    description - this should return all employees, unfiltered

getEmployeeByUuid(...)

    path variable - employee UUID
    output - employee
    description - this should return a single employee based on the provided employee UUID

createEmployee(...)

    request body - attributes necessary to create an employee
    output - employee
    description - this should return a single employee, if created, otherwise error

## Implementation Notes

The API uses a conventional controller-service split:

- `EmployeeController` owns HTTP routing and response semantics.
- `EmployeeService` defines the application operations.
- `InMemoryEmployeeService` provides thread-safe, in-memory storage and two deterministic seed employees.
- `EmployeeCreateRequest` keeps client-controlled input separate from server-controlled fields such as UUID and termination date.
- `ApiExceptionHandler` returns consistent `404` and validation-error responses.

### REST contract

| Method | Path | Result |
| --- | --- | --- |
| `GET` | `/api/v1/employee` | `200 OK` with all employees |
| `GET` | `/api/v1/employee/{uuid}` | `200 OK`, or `404 Not Found` |
| `POST` | `/api/v1/employee` | `201 Created`, including a `Location` header |

The create endpoint validates required names, salary, age, title, email, and hire date. Names are capped at 100 characters, job titles at 150, and email addresses at 254; salary must be positive, age must be 16–120, and the hire date cannot be in the future. UUIDs and full names are generated by the application. A termination date is intentionally excluded from creation because a newly created employee is active.

Malformed UUIDs return a sanitized `400 Bad Request`; valid but unknown UUIDs return `404 Not Found`. Validation failures return a consistent JSON response with per-field messages.

### Design decisions and scope

- The supplied `Employee` interface and `/api/v1/employee` route are preserved.
- `ConcurrentHashMap` is sufficient for the requested mock persistence and safe for concurrent webhook requests. `getAllEmployees` returns a sorted, structurally unmodifiable list snapshot for deterministic output.
- The request DTO prevents callers from controlling server-owned fields (`uuid`, `fullName`, and termination state).
- A database, repository abstraction, pagination, mapping framework, and OpenAPI tooling were deliberately omitted because the prompt asks for only three endpoints and no persistence layer.
- The `Location` header is derived from the active request URI rather than duplicating the controller path.

### Test coverage

The focused JUnit 5 suite covers service creation/retrieval, stable immutable snapshots, derived-name synchronization, authenticated and unauthenticated access, invalid credentials, successful listing and creation, `201`/`Location` behavior, valid-but-missing and malformed UUIDs, field validation, maximum-length rejection, and future-date rejection.

### Security

Every endpoint requires HTTP Basic authentication. Sessions are stateless, unknown routes are denied, and CSRF is disabled because this API is intended for non-browser webhook clients. Configure credentials at runtime using Spring Boot's standard `SPRING_SECURITY_USER_NAME` and `SPRING_SECURITY_USER_PASSWORD` environment variables; startup fails closed when either value is missing. Do not commit credentials. TLS should be terminated by the deployment platform so Basic credentials are never transmitted over plaintext HTTP.

### Run locally

Java 17 is required. The commands below use Bash. If your terminal uses zsh (the macOS default), run `bash` first.

```bash
export SPRING_SECURITY_USER_NAME=employee-webhook
read -r -s -p "Local API password: " SPRING_SECURITY_USER_PASSWORD
export SPRING_SECURITY_USER_PASSWORD
./gradlew bootRun
```

Example request:

```bash
curl --user "$SPRING_SECURITY_USER_NAME:$SPRING_SECURITY_USER_PASSWORD" \
  http://localhost:8080/api/v1/employee
```
